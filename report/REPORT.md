# Report — AmazonHelp Twitter Support Agent

## ⚠️ Data disclosure (read this first)

This was built in a sandboxed environment with **no internet access**, so the
real Kaggle `thoughtvector/customer-support-on-twitter` dataset could not be
downloaded. Everything below — the data, the golden set, the numbers — runs
on a **synthetic stand-in with the identical schema**, generated by
`src/generate_sample_data.py` (see its docstring for exact templates). The
numbers in this report are real outputs of the real pipeline, but they are
outputs on synthetic data and should be read as **"does the pipeline and eval
harness work end-to-end and produce sane-looking numbers,"** not as
"here is how good the agent is on real AmazonHelp tweets." Re-running steps
1–4 of the README against the real Kaggle CSV, with a genuinely hand-labeled
golden set, is required before these numbers mean anything for real.

## 1. Problem framing

**Brand:** AmazonHelp. Chosen for volume, order-centricity, and templated-
enough replies that retrieval-grounding is a fair approach to evaluate.

**What "good" means for this agent, in priority order:**
1. **Never cause harm.** Never leak account/payment info, never confidently
   promise something the brand can't guarantee (a specific refund date,
   confirming a cancellation that didn't happen).
2. **Escalate the right things.** Recall on ESCALATE matters more than
   precision — an unnecessary escalation costs agent time; a missed one
   costs customer trust or money.
3. **Sound like this brand, not a generic bot.** Replies should follow the
   pattern of how this brand has actually resolved similar issues before
   (grounding), not just be fluent.
4. **Be fast and cheap enough to run on real volume**, which is why
   retrieval uses TF-IDF, not embeddings, and why escalation is rule-based,
   not a second LLM call.

**What I chose not to build:**
- **Multi-turn dialogue state.** The agent scores/replies to one inbound
  message at a time, grounded on retrieved history, but doesn't track "we've
  already asked this customer for their order number in this thread." A real
  deployment needs that; it's out of scope for this assignment's time budget.
- **Sentiment/frustration as a separate model.** Folded into escalation as
  keyword/pattern rules instead (decision log #15) — simpler, less accurate
  on subtle cases.
- **Embedding-based retrieval.** TF-IDF only (decision log #6) — fine at this
  scale, a known limitation at larger scale.
- **PII handling / redaction.** Not built. A real system touching customer
  order numbers and (potentially) names needs this; flagged as next-week work.
- **Auto-sending replies.** The agent drafts and decides escalate/auto-handle;
  it does not actually post anything. Out of scope — deliberately, since
  "should this be reviewed before going out" is a distinct, harder question
  from "should this be handled at all," and conflating them would understate
  risk.

## 2. Results vs. baselines

Run on 180 golden examples (`eval/eval_results.json`, reproducible via
`python eval/run_eval.py`). No `ANTHROPIC_API_KEY` was available in this
sandbox, so the "LLM" rows below are actually its **keyword-fallback** and
**heuristic-judge fallback** — flagged explicitly, see §4.

### Intent classification

| Model | Accuracy | Macro-F1 |
|---|---|---|
| Trivial baseline (majority class) | 0.10 | 0.02 |
| TF-IDF + Logistic Regression baseline | **0.90** | **0.91** |
| LLM classifier (keyword-fallback, no API key) | 0.60 | 0.58 |

### Escalation decision (positive class = ESCALATE)

| Metric | Value |
|---|---|
| Precision | 0.80 |
| Recall | **0.40** |
| F1 | 0.53 |
| Accuracy | 0.65 |

### Reply quality (LLM-judge, heuristic fallback, n=40 AUTO_HANDLE cases)

| Dimension | Avg (1–5) |
|---|---|
| Grounded | 3.95 |
| Correct | 5.00 |
| Safe | 4.85 |
| Tone | 5.00 |
| **Overall** | **4.70** |

### Judge–human agreement (placeholder calibration set, n=30 — see §4)

Pearson r = **-0.08**, % within 1 point = **73.3%**.

## 3. Failure analysis — top 5 failure modes

1. **Keyword-fallback intent classifier loses to the TF-IDF baseline
   (0.60 vs 0.90 accuracy).**
   Example: *"you charged my card twice for order 445566, this is a scam,
   I'm calling my lawyer"* → keyword fallback predicts `where_is_my_order`
   (misses "charged twice" because the actual text is "charged my card
   twice" and the rule looks for the exact substring "charged twice").
   Hypothesis: keyword rules are brittle to natural phrasing variation in a
   way a trained model isn't, even a simple TF-IDF one. This is the core
   finding of §4.

2. **Escalation recall is low (0.40) — the agent under-escalates.**
   Example: *"@AmazonHelp received a used/opened item marked as new, order
   X, that's basically fraud"* — gold label ESCALATE (risk language present:
   "fraud"), but if intent is mispredicted (see failure #1) the downstream
   escalation rules that depend on intent (`ESCALATE_INTENTS`) don't fire,
   and if the risk-keyword check also narrowly misses phrasing, it slips to
   AUTO_HANDLE. Hypothesis: escalation errors compound from upstream intent
   errors — this is a pipeline-design risk, not just an escalation-rule
   weakness.

3. **Reply grounding drops when historical replies are near-duplicate
   templates.** In this synthetic set, the "historical" replies were
   generated from only 10 fixed templates, so grounding always finds a
   near-perfect match — this inflates the grounded score (3.95) in a way
   real data won't replicate, since real historical brand replies vary far
   more in phrasing even for the same underlying resolution.

4. **Judge–human "agreement" is not actually meaningful here (Pearson r ≈
   -0.08).** Both the judge and the calibration "human" scores are
   synthetic/heuristic in this sandbox run, generated independently, so
   there's no real signal for them to agree on — this number is a canary
   that the calibration step *ran*, not evidence the judge is trustworthy.
   This is intentional and disclosed — see §4.

5. **Escalation logic doesn't catch severity within an intent.** E.g. a
   generic `product_defect` (a cracked lamp) and a safety-relevant one (a
   smoking mixer) get the same rule treatment unless risk keywords happen to
   fire. Hypothesis: intent alone is too coarse a signal for escalation;
   would need either finer-grained sub-intents or a severity classifier.

## 4. "What is misleading about my headline number?"

If I only reported the reply-quality overall score (**4.70/5**) and called
it a day, that would be actively misleading, for several stacked reasons:

- **The "LLM" classifier and judge numbers in this report are not LLM
  numbers.** No API key was available in this sandbox, so both fell back to
  crude heuristics (a keyword-rule classifier, a length/keyword-based judge).
  The 4.70 reply-quality score and the 0.60 intent accuracy are measuring
  the *fallback logic*, not the system I actually designed to be evaluated.
  Anyone citing "4.70/5 reply quality" without this caveat is citing the
  wrong system.
- **The eval data is synthetic**, generated by the same small set of
  templates used to build the retrieval index, so "grounding" is
  artificially easy — real brand replies are far less templated, and I'd
  expect the grounded-dimension score to drop meaningfully on real data.
- **The golden set labels are not human-labeled.** They were assigned
  programmatically by the same script that wrote the templates, so
  intent-accuracy numbers reflect "did the classifier reproduce the label
  the generator used," not "did the classifier get real ambiguous cases
  right." Real customer tweets are messier and more ambiguous than any of
  these templates.
- **Escalation precision (0.80) looks fine in isolation, but recall (0.40)
  is the number that matters, and it's bad.** A headline "80% precision"
  claim without pairing it with recall would hide that the agent misses 6 of
  every 10 cases that should have gone to a human in this eval.
- **The judge–human agreement number (r ≈ -0.08) looks like a red flag, and
  it should — but it's a red flag about the placeholder calibration data,
  not (necessarily) about a production judge.** Reporting it without this
  context would either wrongly discredit the judge approach or, worse, get
  quietly dropped from a future report once it's "just a number that
  exists," at which point it stops doing its job of keeping the judge
  honest.

**Bottom line:** every number in §2 needs the "on synthetic data, largely
via fallback logic" caveat attached, every time it's repeated, not just in
this section.

## 5. What I'd do next with one more week

1. Download the real Kaggle CSV, rerun `data_prep.py`, and hand-label a real
   180–250-example golden set per the stratified protocol in
   `eval/build_golden_set.py` (with a second labeler on 20% for kappa).
2. Get real API access and rerun everything — replacing every fallback
   number in §2 with real LLM-classifier / real-judge numbers, and compare
   the two directly (this report's most interesting finding — fallback
   underperforming a cheap trained baseline — might or might not hold once
   it's a real LLM).
3. Run a real human-rating pass (even just me, blind, on 30–50 examples) to
   replace the placeholder judge-human calibration set, and report weighted
   Cohen's kappa per rubric dimension, not just overall Pearson r.
4. Build a confusion matrix for intents and specifically dig into whether
   `refund_request` (which has both "still waiting" and "thanks, it arrived"
   phrasings, see golden set case) needs to be split into two intents —
   the "resolved" version should probably never even reach the agent.
5. Add a severity/urgency signal (either a small classifier or a stronger
   rule set) so escalation isn't purely intent + keyword-based (failure
   mode #5) — this is the highest-leverage fix given escalation recall is
   the weakest headline number.
6. Swap TF-IDF retrieval for embeddings and re-measure whether grounding
   quality actually improves on more realistically varied real replies, or
   whether it was already good enough at this data volume.
